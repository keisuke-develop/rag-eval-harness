# ADR 0003: 生成の評価に LLM-as-a-judge を使わない

- 状態: 採用
- 日付: 2026-09-21

## 背景

生成された回答の良し悪しを測る方法として、別の LLM に採点させる方式（LLM-as-a-judge）が広く使われている。自然な文章を柔軟に評価でき、実装も容易だ。

一方で、この道具の目的は**条件を変えたときのスコア差を比較すること**にある。採点者自体がばらつく仕組みを入れると、スコアが動いたときに「条件が効いた」のか「採点が揺れた」のかを切り分けられない。

## 決定

**生成側の評価は、構造化出力による根拠の照合で行う。LLM に採点させない。**

生成時に、回答本文と同時に「根拠として使ったチャンクID」を構造化出力で返させ、それを正解根拠と機械的に照合する。

```json
{
  "answer": "...",
  "cited_chunk_ids": ["doc12#c3"],
  "abstained": false
}
```

評価する項目は以下の2つに絞る。

| 指標 | 判定方法 |
|---|---|
| 根拠一致率 | `cited_chunk_ids` が正解根拠の span を含むチャンクと一致するか |
| 棄権率 | 答えられない質問に対して `abstained: true` を返したか |

## 理由

- **決定的に判定できる。** 同じ入力に対して必ず同じ評価結果になるため、条件間の差がそのまま比較できる
- **採点コストがゼロ。** 実験を何度回しても評価のための追加 API 呼び出しが発生しない
- **測っていないことが明確になる。** 回答の自然さ・網羅性・簡潔さは測れないが、測れないことが自分にも読み手にもはっきり分かる。LLM-as-a-judge は「なんとなく総合的に良い」という曖昧なスコアを返すため、何を測ったのかが不明瞭になりやすい

## 結果

- 回答の品質のうち、文章としての良さは評価対象外になる。この制約は README と docs/02 に明記する
- 生成モデルに構造化出力の指示が必要になる。出力が壊れた場合は Pydantic の検証で弾き、失敗として記録する
- 「根拠は正しいが回答が不十分」というケースを検出できない。これは既知の限界として受け入れる

## 検討した代替案

**LLM-as-a-judge を併用する**：参考値として並記する案も考えたが、表に載っている数字は必ず読み手に比較されるため、性質の違う指標を並べるのは誤解を招く。採らなかった。

**人手評価**：最も正確だが、実験を6パターン回す前提では現実的でない。将来、最良条件が絞れた段階でサンプル抽出して確認する方が費用対効果が高い。
