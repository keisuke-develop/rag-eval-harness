# 評価設計

作成日: 2026-09-21

このリポジトリの中心。**何を良しとするかを、パイプラインを書く前に決める。**

---

## 1. 評価を2層に分ける

RAG の精度が悪いとき、原因は「関連する文書を引けていない」か「引けているのに答えられていない」のどちらかに分かれる。ひとまとめの指標で測ると、どちらを直せばいいか分からなくなる。そのため検索側と生成側を分けて測る。

| 層 | 問い | 指標 |
|---|---|---|
| 検索 | 正解根拠を引けているか | Recall@k、MRR |
| 生成 | 引けた文脈に基づいて答えられているか | 根拠一致率、棄権率 |

## 2. 検索側の指標

### Recall@k

上位 k 件のなかに正解根拠のチャンクが含まれていた質問の割合。

```
Recall@k = (正解根拠が top-k に含まれた質問数) / (全質問数)
```

**なぜこれを主指標にするか。** RAG では、正解根拠さえ文脈に入っていれば生成側が拾える可能性が残る。逆に検索で落ちたら生成では絶対に取り返せない。つまり Recall@k は上限を決める指標であり、ここが低いまま生成側をいじっても意味がない。

### MRR（Mean Reciprocal Rank）

正解根拠が何位に出たかの逆数の平均。

```
MRR = (1/N) * Σ (1 / 正解根拠の最上位順位)
```

**なぜ併用するか。** Recall@5 は「5位以内に入ったか」しか見ないため、1位に出ても5位に出ても同じ扱いになる。実際には上位に出るほど生成側が拾いやすい。top-k を絞ったときに何が起きるかを予測するには順位の情報が要る。

### 採用しなかった指標

| 指標 | 見送った理由 |
|---|---|
| Precision@k | 本評価セットは1問1正解根拠のため、Precision は Recall と自明な関係になり情報量が増えない |
| nDCG | 根拠に段階的な関連度を付ける設計にしていないため、MRR 以上の情報を持たない |

## 3. 生成側の指標

### 根拠一致率

生成された回答が、正解根拠のチャンクに含まれる情報だけで構成されているかの割合。

判定は、生成時に回答と同時に「根拠として使ったチャンクID」を構造化出力で返させ、それが正解根拠と一致するかで見る。LLM に採点させる方式（LLM-as-a-judge）は採らない。理由は [adr/0003-no-llm-judge.md](adr/0003-no-llm-judge.md) に書いた。

```json
{
  "answer": "...",
  "cited_chunk_ids": ["doc12#c3"],
  "abstained": false
}
```

### 棄権率

文脈に答えが無いときに「分からない」と返せた割合。

**なぜ測るか。** RAG で実務上いちばん困るのは、検索に失敗したときに無いものをでっち上げることだ。評価セットには意図的に**答えられない質問を1割ほど混ぜる**。ここで棄権できるかどうかは、精度の数字とは別に見ておく価値がある。

## 4. 評価セットの作り方

### 構成

| 項目 | 内容 |
|---|---|
| 件数 | 40〜60 件 |
| 内訳 | 答えられる質問 90% ／ 文脈に答えが無い質問 10% |
| 形式 | JSONL。1行1質問 |

```json
{"qid": "q001", "question": "...", "gold_chunk_ids": ["doc03#c7"], "answerable": true}
{"qid": "q042", "question": "...", "gold_chunk_ids": [], "answerable": false}
```

### 作成の手順

1. コーパスから、内容の異なる文書を万遍なく選ぶ
2. 各文書から、その文書を読まないと答えられない質問を作る
3. 正解根拠のチャンクIDを記録する
4. **一晩置いてから自分で解き直し**、質問文だけを見て根拠にたどり着けるかを確認する
5. たどり着けなかった質問は、曖昧なので作り直す

4 を入れているのは、作った直後は自分の記憶で答えられてしまい、質問の曖昧さに気づけないため。

### 質問を作るときの基準

| 基準 | 理由 |
|---|---|
| 固有名詞や数値を問う質問を半分以上入れる | 正解判定が揺れない |
| 文書をまたぐ質問は入れない | 1問1正解根拠を崩すと Recall の解釈が難しくなる |
| コーパスの表現をそのまま使わない | 表層一致で当たってしまい、検索の実力が測れない |
| 答えられない質問は「もっともらしいが載っていない」ものにする | 明らかに無関係な質問では棄権の難易度が低すぎる |

### チャンクIDの安定性

チャンク分割の条件を変えるとチャンクIDも変わるため、正解根拠は**チャンクIDではなく文字オフセット範囲**で持つ。実行時に、その範囲を含むチャンクを正解とみなす。

```json
{"qid": "q001", "question": "...", "gold_spans": [{"doc": "doc03", "start": 1420, "end": 1655}]}
```

これをやらないと、チャンクサイズを変えた瞬間に評価セットが使えなくなる。**この設計がないと、そもそもチャンクサイズの比較実験が成立しない。**

## 5. コーパス

評価に使う文書は、再配布可能なライセンスの公開文書のみを使う。

| 出典 | ライセンス | 用途 |
|---|---|---|
| （選定中） | （記載する） | （記載する） |

選定の条件は以下。

- 再配布が明示的に許諾されていること（ライセンス文を `datasets/corpus/LICENSE-NOTICE.md` に転記する）
- 日本語であること（実務で扱う対象に合わせる）
- 1文書あたり数千字程度で、チャンク分割の挙動が観察できる長さがあること
- 個人情報・機微情報を含まないこと

## 6. 測定時の固定条件

比較を成立させるために、実験中は以下を固定する。

| 項目 | 値 | 理由 |
|---|---|---|
| temperature | 0.0 | 生成のばらつきを抑える |
| seed | 42 | 同上 |
| 評価セット | 実験期間中は変更しない | 途中で変えると過去の結果と比較できなくなる |
| プロンプト | 実験軸にする場合を除き固定 | 暗黙に変わると原因の切り分けができなくなる |

評価セットを更新した場合は、バージョンを上げて過去の結果と混ぜない。

## 7. 結果の読み方

スコア差をどう扱うかを先に決めておく。

- 評価セットが 50 件規模のため、**数ポイントの差は誤差の範囲**として扱う
- 有意差の主張はしない。「傾向としてこう動いた」までに留める
- 差が出た条件については、個別の質問まで降りて何が起きたかを確認し、考察に書く

この制約を先に書いておくのは、後から都合よく解釈しないため。
