# ADR 0002: 差し替え可能な箇所を4つに限定する

- 状態: 採用
- 日付: 2026-09-21

## 背景

比較のための道具なので、あらゆる箇所を差し替え可能にしたくなる。プロンプトも、前処理も、後処理も、評価指標も、プラグインとして外から注入できるようにすれば、どんな実験でもできる。

しかしそうすると、結果が動いたときに「何が効いたのか」を特定できなくなる。可変点の数だけ交絡が増える。加えて、抽象化のコードが増えてリポジトリが読みにくくなり、「読む人に設計判断が伝わる」という目的からも遠ざかる。

## 決定

**差し替え可能にするのは、以下の4点だけとする。**

| 差し替え点 | Protocol | 理由 |
|---|---|---|
| チャンク戦略 | `Chunker` | 実験1・2の主軸 |
| 埋め込みプロバイダ | `Embedder` | 実験5の主軸。モデル差の影響を見る |
| Vector DB | `VectorStore` | 実装が特定製品に固定されていないことを示すため |
| 再ランカー | `Reranker` | 実験4の主軸。有無の切り替えが必要 |

以下は**あえて固定する**。

- プロンプトテンプレート（実験軸にする場合のみ、experiments の YAML で明示的に上書きする）
- 生成プロバイダ（差し替えたくなったら実装を足すが、Protocol は切らない）
- 評価指標（コードに直接書く。増やすときは実装を足す）
- 前処理・後処理（そもそも入れない）

## 理由

- 実験の軸として実際に使う4つだけを可変にすれば、交絡は最小限に抑えられる
- Protocol は構造的部分型なので、継承関係を強制しない。テストでダミー実装を差し込むのも簡単
- 「何を可変にし、何を固定したか」自体が設計判断であり、それを明示することに価値がある

## 結果

- 5つ目の軸を試したくなったら、Protocol を1つ足すという明示的な判断が必要になる。安易に増えない
- 評価指標を差し替え式にしていないため、指標を増やすには `evaluate.py` を直接触る。そのぶん指標の定義が1箇所に集まり、読みやすくなる

## 検討した代替案

**すべてをプラグイン化する**：柔軟性は最大になるが、設定の組み合わせが爆発し、実験結果の解釈が困難になる。またコード量が増え、読み手が設計意図を追いにくくなる。この道具の目的は汎用性ではなく「比較を成立させること」なので、採らなかった。

**一切抽象化しない**：最も読みやすいが、チャンク戦略と埋め込みモデルの比較ができない。実験計画が成立しないため却下。
