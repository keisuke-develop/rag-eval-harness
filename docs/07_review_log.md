## 修正の内訳

### 第1回 正解チャンクが空でも静かに集計されていた

`score()` は、答えられる質問の正解チャンクが0個のとき、**エラーにせず単なる不正解として
数えていた。** チャンクは文書を隙間なく覆うので、これが起きるのは
**評価セットの文字オフセットがコーパスの外を指しているとき**——つまり評価が壊れているとき。

このリポジトリは「正解根拠を文字オフセットで持つ」ことを土台にしているので、
その土台が壊れたときに低いスコアとして紛れ込むのは、いちばん避けたい失敗の仕方だった。
例外を投げ、`uv run python datasets/build_qa_set.py --check` を案内するようにした。

**実行時点では0件**なので、スコアは1つも動いていない。将来の事故のための検知。

### 第4回 同じ条件を2回書いても弾けなかった

最初はラベルの重複だけを見ていたが、テストで**想定が外れた。**
同じ条件を2回書いても、軸が動かないぶんラベルは `variant1` / `variant2` と
別々に付くので、重複として検出できない。条件そのもの（解決後の設定）を比べる形に直した。

副産物として、**設定の誤りが実験ファイルを読んだ時点で出るようになった。**
重複の検査が `resolve()` を通すため、`overlap >= size` のような値の誤りも
実行前に分かる。既存のテストはこの変化に合わせて書き直した。

### 第5回 report の表に、どのプロバイダで測ったかが出ていなかった

`rageval report` が出す表には、ダミー実装での結果と実APIでの結果が並びうる。
そこに**プロバイダの情報が無い**と、読み手が区別できない。
このリポジトリが繰り返し戒めている「測っていないものを測ったように書く」を、
生成物のほうでやってしまっていた。各実験の見出しに
「埋め込み hashing / 生成 quote」を出すようにした。

### 第6回 使用量の合計を出していなかった

`Usage.merge` が実装もテストもされているのに、**本番コードから一度も呼ばれていなかった。**
テストが通るぶん、動いているように見える死にコードだった。

原因は、docs/03 が「入出力トークン数と推定コストを記録する」と定めているのに、
**条件ごとの内訳しか出しておらず、実験1本ぶんの合計を出していなかった**こと。
`result.json` に `total_usage` を足して、`merge` を本来の用途で使うようにした。

### 第18回 生成の失敗を記録する経路が未検証だった

ADR 0003 は「出力が壊れた場合は Pydantic の検証で弾き、失敗として記録する」と決めている。
その記録の経路（`runner.py`）が、**カバレッジ上ずっと通っていなかった。**
壊れたらスコアに紛れて見えなくなる仕組みなのに、仕組み自体が効いているか誰も知らない状態。

JSON にならない応答を返すモックで通しの試験を足した。
あわせて、応答の形が違う場合・複数軸の理由の表示・評価セットの版の記録も試験を足した。

# 実利用観点の評価

20回のレビューはコードを読む側の確認だった。**カバレッジは「コードが通ったか」しか見ておらず、
使ったときにどうかは測っていない。** そこで、利用者が実際にやることを自分でやってみた。

## 見つかったもの

### 1. 設定を1文字打ち間違えると、38行のトレースバックが出ていた

`top_k` を `top_K` と書いただけで、Python のフレームが延々と流れ、
**本当の原因は一番下に、pydantic の英語表現で出る**。

```
ValidationError: 1 validation error for ExperimentConfig
retrieve.top_K
  Extra inputs are not permitted [type=extra_forbidden, input_value=3, ...]
```

`config.py` に日本語で丁寧に書いたメッセージ（「1実験につき動かす軸は1つ」など）も、
同じように39行のフレームの底に埋もれていた。**テストは `pytest.raises` で通っていた。**
例外が上がることは確かめていたが、画面に何が出るかは誰も見ていなかった。

**直した結果:**

```
エラー: 実験ファイルの条件が正しくない: .../typo.yaml
  retrieve.top_K: 指定できないキー。書けるのは top_k, rerank, candidates
```

38行 → 2行。どのキーが違うかを指し、正しい候補まで挙げる。
トレースバックは実装の不具合を追うためのもので、設定の書き間違いに出すものではない。

存在しない実験ファイル、コーパスのパス誤り、未知の指標名も同様に直した。
**「画面に何が出るか」を見るテストを5件足した**ので、また埋もれたら落ちる。

### 2. 条件を変えて回し直すと、過去の測定が黙って消えていた

同じ `run_id` で回すと出力先が同じになる。試したところ、

```
1回目（top_k=5） : baseline 0.562 0.337
2回目（top_k=10）: baseline 0.604 0.343   ← 同じ場所に上書き
```

**1回目の結果は跡形もなく消える。** docs/01 は「実験ファイルを後で編集しても
過去の結果の条件が変わらないように」と書いているのに、回し直した時点で失われていた。
S3 に上げる側は実行時刻で分けているのに、手元側は分けていないという不一致もあった。

**比較できるようにするための道具が、比較の材料を消していた。**

**直した結果:** スナップショットを突き合わせ、**条件が違えば実験を回す前に断る**。
条件が同じなら（この道具は決定的なので結果も同じ）そのまま上書きする。
消してよいときだけ `--force`。

### 3. 規模の限界を数字にした

docs/06 に「コーパスが大きいと OOM になる」と曖昧に書いていた受容リスクを、実測した。

| 倍率 | チャンク | 索引 | 1問あたり | メモリ |
|---|---|---|---|---|
| 1x | 137 | 0.5秒 | 0.1ms | 3MB |
| 50x | 6,850 | 27.3秒 | 2.8ms | 155MB |

すべてチャンク数に線形。外挿すると **AWS の 1GB 設定では約4,000文書が上限**で、
時間ではなくメモリが先に効く。逆に **評価セットを増やす側のコストはほぼゼロ**
（1問0.1msなので53問を500問にしても実行時間は変わらない）と分かった。
これは docs/05 の「次にやるべきこと」の判断材料になる。

## 今回埋めた穴

### コーパスに BOM が付いていると、その文書のオフセットが全部ずれる

`read_text(encoding="utf-8")` は BOM を1文字として残す。
Windows のメモ帳などで保存すると付く。**評価セットを作った時点と読む時点で
BOM の有無が変われば、正解根拠が静かに1文字ずれた場所を指す。**

黙って剥がすと、剥がす前に作った評価セットと辻褄が合わなくなるので、
**読み込み時に止める**ようにした。いまのコーパス12文書に BOM は無い。

### 空の文書が黙って無視されていた

0バイトの `.txt` はチャンクを1つも生まないので、
**入れたはずの文書が検索に出ないことに気づけない。** 読み込み時に止めるようにした。

### 壊れた `result.json` で `report` が59行のトレースバックを出していた

`run` の側は実利用観点の評価で直したが、`report` は手つかずだった。
どのディレクトリが壊れているかを言って止まるようにした。

### 境界値

| 確かめたこと | 結果 |
|---|---|
| `top_k` がチャンク数より大きい | あるだけ返し、順位を詰めて振り直す |
| `top_k` = 1 | 正常 |
| `overlap` = `size` - 1（許される上限） | 分割が進み、全文を覆う |
| 文書の長さがちょうど1チャンク | 1件だけ生成 |
| 根拠が本文の先頭／末尾にある | どちらも覆われる |

### Unicode

`𠮷` や絵文字（サロゲートペア）を含む本文で、オフセットが本文を正しく指すことを確認。
Python の文字列は符号位置単位なので、UTF-8 のバイト数（29）と長さ（9）が違っても破綻しない。
**バイト単位と取り違えた実装に変わったら、このテストが落ちる。**

# 追加の実験と、その結果わかったこと（3周目）

「Git 以外で進められる残作業を進める」ぶんの記録。実験を3本足し、
インフラ側の残件を1つ潰した。詳細は [05_offline_results.md](05_offline_results.md)。

## 足した実験

| # | 何を動かしたか | 結果 |
|---|---|---|
| 009 | チャンクサイズ 3種 × 位相 8種（24条件） | 512 が 256 より +0.034。t=1.78 で**判定できない** |
| 010 | 再ランクに渡す候補数 5 / 10 / 20 / 50 / 137 | Recall 0.562 → **0.812**（+0.250） |
| — | 評価セットの必要件数の見積り | いまの48問で検出できるのは **0.066 以上**の差 |

## 実験010 が、これまでの実験の読み方を変えた

候補数を全チャンク（137）にすると、埋め込みの順位は使われない。
**文字 n-gram の一致だけで並べ替えたほうが、ハッシュ化埋め込みより 0.250 良い。**

ノイズ幅 0.083 の3倍で、今回見つけた中で最大の差だった。
これは 001〜009 が**弱い検索器のうえでの効果を測っていた**ことを意味する。
実APIで最初に回すべき実験を 003（top-k）から **005（埋め込みモデル）** に入れ替えた。

## 実験009 で、統計の扱いを一度まちがえた

2群の平均を比べるのに、片方の群の標準誤差（0.016）をそのまま使って
「効果あり」と書きかけた。2群の差の標準誤差は √2 倍（0.023）で、t=1.6。
**判定できない**が正しい。位相を8つに増やして測り直しても t=1.78 で変わらなかった。

対応のある比較（質問ごとの差）も試したが、標準誤差は**むしろ大きく**なった（0.033）。
理由を追うと、チャンクサイズを変えると**当たる質問の顔ぶれが入れ替わる**（18問改善・14問悪化・16問同じ）。
実験008 で再ランクに効いた「対応のある比較で境界の運を消す」手は、
**分割そのものが変わる比較では効かない。**

## インフラ側：送信専用のセキュリティグループ

AWS 検証時は既定の SG を使っていた（[06_security_review.md](06_security_review.md) で △ としていた箇所）。
既定 SG は同じ SG 内からの受信を許すので、送信しかしないタスクには広すぎる。
443 の送信だけを許し**受信ルールを1つも持たない** SG をテンプレートに足した。

`VpcId` を渡さなければ作らない（既存の手順が壊れないように）。
cfn-lint と checkov（46件通過・失敗0件）は通るが、**この SG を載せた状態では実機確認していない。**
AWS のリソースは検証後に全削除済みで、作り直すと費用が出るため。

`GroupDescription` は ASCII しか通らず、日本語を書いて cfn-lint に落とされた。
テンプレート内の他の説明文は日本語のままで問題ない。

# 観点を洗い出してからの総点検（4周目）

「やるべきことを先に洗い出してタスクにし、進められるものを全部進めてから、
内容のレビューを10回繰り返す」ぶんの記録。

観点を14本（計画・実装・テスト・型・アプリ層セキュリティ・公開適性・依存・

# 実APIの鍵を入れた日に起きたこと（6周目）

鍵を用意していただき、動作確認のコマンドを回した。**実験は1本も回せていない。**
残高が無かったため。ただし、その過程で**守りの穴が1つ見つかった。**

## いちばん重大だったこと：本物の鍵がコミット対象のファイルに入っていた

案内は「`.env.example` を写して `.env` に鍵を入れる」だった。
実際には **`.env.example` のほうに本物の鍵が書き込まれていた。**
`.env.example` は Git 管理下で、このリポジトリは public。

**コミットも push もされていない。** 気づいたのは、実行の前に
`git status` の差分をたまたま見たからで、**仕組みが止めたわけではない。**

### なぜ止まらなかったか

| 守り | 効いたか | 理由 |
|---|---|---|
| `.gitignore` | ❌ | `.env` は無視するが、`.env.example` は**意図的に無視しない** |
| `detect-secrets`（CI） | ❌ | **見本ファイルを検査対象から外す** |
| `deploy/package_source.py` | ❌ | AWS へ送る zip の検査で、`.env.example` は明示的に許している |

2つめが分かったのは、同じ内容を4つの形で試したときだった。

| ファイル名 | 中身 | 検出 |
|---|---|---|
| `t1.env.example` | `OPENAI_API_KEY=sk-proj-…` | **されない** |
| `t2.txt` | 同じ | される |
| `t3.py` | 同じ | される |
| `t4.yaml` | 同じ | される |

**利用者に「これを写せ」と案内しているファイルだけが、守られていなかった。**

### 直したこと

`tools/check_no_secrets.py` を書いて CI に載せた。
提供元ごとの接頭辞（`sk-proj-` / `sk-ant-` / `ghp_` / `AKIA` など）のあとに、
**十分な長さと散らばりを持つ文字列**が続いていたら落とす。

差し込み用の値を落とさないことも同時に固定した。
`sk-your-key-here` や AWS が文書で使う例示キーで落ちるようだと、
**検査そのものが無視されるようになる**ため、そちらのテストのほうを厚くしてある。

検査の出力に**鍵そのものを載せない**（接頭辞と長さだけ）。出力はログに残る。

## 429 が2つの意味を持っていた

残高が無いときも、呼び出しが速すぎるときも 429 が返る。**やることは正反対**で、
前者は待っても直らない。最初の案内は「レート制限か残高不足」とまとめてしまっていて、
どちらなのか分からなかった。

原因は、応答の本文を先頭 200 文字で切っていたこと。
OpenAI の応答は長い `message` が先に来るので、区別に要る `type` と `code` が落ちる。

切る前に `type` / `code` を取り出して先頭に置くようにした。

```
429 https://api.openai.com/v1/embeddings [insufficient_quota / credit_balance_exhausted]:
  You have no credits remaining. ...
残高が無い。platform.openai.com の Billing でクレジットを追加すること（待っても直らない）
```
