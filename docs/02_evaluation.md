# 評価設計

作成日: 2026-09-21

このリポジトリの中心。**何を良しとするかを、パイプラインを書く前に決める。**

---

## 1. 評価を2層に分ける

RAG の精度が悪いとき、原因は「関連する文書を引けていない」か「引けているのに答えられていない」のどちらかに分かれる。ひとまとめの指標で測ると、どちらを直せばいいか分からなくなる。そのため検索側と生成側を分けて測る。

| 層 | 問い | 指標 |
|---|---|---|
| 検索 | 正解根拠を引けているか | Recall@k、MRR |
| 生成 | 引けた文脈に基づいて答えられているか | 根拠一致率、棄権率 |

## 2. 検索側の指標

### Recall@k

上位 k 件のなかに正解根拠のチャンクが含まれていた質問の割合。

```
Recall@k = (正解根拠が top-k に含まれた質問数) / (全質問数)
```

**なぜこれを主指標にするか。** RAG では、正解根拠さえ文脈に入っていれば生成側が拾える可能性が残る。逆に検索で落ちたら生成では絶対に取り返せない。つまり Recall@k は上限を決める指標であり、ここが低いまま生成側をいじっても意味がない。

### MRR（Mean Reciprocal Rank）

正解根拠が何位に出たかの逆数の平均。

```
MRR = (1/N) * Σ (1 / 正解根拠の最上位順位)
```

**なぜ併用するか。** Recall@5 は「5位以内に入ったか」しか見ないため、1位に出ても5位に出ても同じ扱いになる。実際には上位に出るほど生成側が拾いやすい。top-k を絞ったときに何が起きるかを予測するには順位の情報が要る。

### 採用しなかった指標

| 指標 | 見送った理由 |
|---|---|
| Precision@k | 本評価セットは1問1正解根拠のため、Precision は Recall と自明な関係になり情報量が増えない |
| nDCG | 根拠に段階的な関連度を付ける設計にしていないため、MRR 以上の情報を持たない |

## 3. 生成側の指標

### 根拠一致率

生成された回答が、正解根拠のチャンクに含まれる情報だけで構成されているかの割合。

判定は、生成時に回答と同時に「根拠として使ったチャンクID」を構造化出力で返させ、それが正解根拠と一致するかで見る。LLM に採点させる方式（LLM-as-a-judge）は採らない。理由は [adr/0003-no-llm-judge.md](adr/0003-no-llm-judge.md) に書いた。

```json
{
  "answer": "...",
  "cited_chunk_ids": ["doc12#c3"],
  "abstained": false
}
```

### 棄権率

文脈に答えが無いときに「分からない」と返せた割合。

**なぜ測るか。** RAG で実務上いちばん困るのは、検索に失敗したときに無いものをでっち上げることだ。評価セットには意図的に**答えられない質問を1割ほど混ぜる**。ここで棄権できるかどうかは、精度の数字とは別に見ておく価値がある。

#### 外部APIに出ない生成では、この指標は動かない

`provider: quote`（最上位ヒットをそのまま引用する決定的な実装）に棄権を判定させようとして、失敗した記録を残しておく。

当初は「検索スコアが閾値を下回ったら棄権する」設計にした。評価セット53件で分布を測った結果は以下。

| 母集団 | 最上位スコアの中央値 | 最大 |
|---|---|---|
| 答えられる質問（48件） | 0.156 | 0.272 |
| 答えられない質問（5件） | **0.197** | 0.258 |

**答えられない質問のほうがスコアが高い。** 閾値をどこに置いても分離できない。語彙の一致率（クエリの文字 n-gram がチャンクにどれだけ含まれるか）に替えても、答えられない質問の最大値 0.396 が答えられる質問の第1四分位 0.180 を上回り、重なりは解消しなかった。

そこで、**`provider: quote` は棄権を判定しない**ことにした。文脈がまったく空のときだけ棄権する。したがってこの条件では棄権率は常に 0 になり、指標として何も測っていない。

判定できないものをそれらしい閾値で判定した風にすると、表に 0.4 のような数字が並び、読む人はそれを意味のある値として比較してしまう。「測っていないものを測ったように書かない」ほうを取った。**この指標が生きるのは、実際の生成モデルを使うときだけ。**

## 4. 評価セットの作り方

### 構成

| 項目 | 基準 | v1.0 の実績 |
|---|---|---|
| 件数 | 40〜60 件 | 53 件 |
| 内訳 | 答えられる質問 90% ／ 文脈に答えが無い質問 10% | 48 件 ／ 5 件（9.4%） |
| 固有名詞・数値を問う質問 | 半分以上 | 42 件（79.2%） |
| 文書あたりの件数 | 偏らせない | 全12文書とも 4 件 |
| 形式 | JSONL。1行1質問 | `datasets/qa_set.jsonl` |

```json
{"qid": "q001", "question": "...", "gold_spans": [{"doc": "doc01_fujisan", "start": 2481, "end": 2529}], "answerable": true, "factoid": true}
{"qid": "q049", "question": "...", "gold_spans": [], "answerable": false, "factoid": true}
```

`factoid` は「固有名詞や数値を問う質問か」を表す。上の基準を機械的に検査するために持たせている。

### 作成の手順

1. コーパスから、内容の異なる文書を万遍なく選ぶ
2. 各文書から、その文書を読まないと答えられない質問を作る
3. 正解根拠のチャンクIDを記録する
4. **一晩置いてから自分で解き直し**、質問文だけを見て根拠にたどり着けるかを確認する
5. たどり着けなかった質問は、曖昧なので作り直す

4 を入れているのは、作った直後は自分の記憶で答えられてしまい、質問の曖昧さに気づけないため。

#### v1.0 で 4 をやった結果

53 件を解き直して、3 件を作り直した。いずれも「答えが1つに定まらない」問題だった。

| qid | 元の質問 | 問題 | 直した内容 |
|---|---|---|---|
| q001 | 富士山の山頂の二等三角点で計測された高さは | 三角点が剣ヶ峰と富士白山の2つあり、さらに剣ヶ峰にも 3775.56 m と 3775.51 m の2つの記載がある | 最高地点の標高（3776.12 m）を問う形に変更 |
| q014 | 組立完了時点の ISS の重量は | 「419トン」と、別の節の「約420トン」で答えが割れる | 同じ文にあり他に記載のないトラス長（108.4 m）を問う形に変更 |
| q026 | 日本国憲法の本文はいくつの章と条文でできているか | 本文の言い回しを10文字そのままなぞっていた | 言い換えて連続一致を6文字に短縮 |

**3件とも、平均スコアには現れないが個別の質問では確実に誤判定になるものだった。**
この手順を飛ばしていたら、Recall が下がったときに「検索が悪いのか設問が悪いのか」を
切り分けられなくなっていた。

### 作り方と検査を分ける

オフセットを人が手で書くと必ずずれるため、人が編集するのは
`datasets/qa_draft.yaml`（質問と、根拠として引用する本文）だけにして、
`datasets/build_qa_set.py` がコーパスを引いてオフセットに変換する。

```bash
uv run python datasets/build_qa_set.py --check   # 検査だけ
uv run python datasets/build_qa_set.py           # qa_set.jsonl を生成
```

生成時に以下を検査し、1件でも引っかかれば生成しない。

| 検査 | 落とす理由 |
|---|---|
| 引用がコーパスに**ちょうど1回**現れる | 0回はタイプミス、2回以上は根拠が一意に定まらない |
| 質問と引用の連続一致が15文字以下 | それ以上は本文を写している。表層一致で当たってしまう |
| 答えられない質問に根拠が付いていない | 棄権率の判定が壊れる |
| 件数・内訳・固有名詞比率が基準の範囲内 | 上の「構成」の表を機械で守る |

生成後の `qa_set.jsonl` は `tests/unit/test_qa_set.py` が検査する。
コーパスを1文字でも動かすとオフセットがずれるため、CI で毎回突き合わせる。

### 質問を作るときの基準

| 基準 | 理由 |
|---|---|
| 固有名詞や数値を問う質問を半分以上入れる | 正解判定が揺れない |
| 文書をまたぐ質問は入れない | 1問1正解根拠を崩すと Recall の解釈が難しくなる |
| コーパスの表現をそのまま使わない | 表層一致で当たってしまい、検索の実力が測れない |
| 答えられない質問は「もっともらしいが載っていない」ものにする | 明らかに無関係な質問では棄権の難易度が低すぎる |

### チャンクIDの安定性

チャンク分割の条件を変えるとチャンクIDも変わるため、正解根拠は**チャンクIDではなく文字オフセット範囲**で持つ。実行時に、その範囲を含むチャンクを正解とみなす。

```json
{"qid": "q001", "question": "...", "gold_spans": [{"doc": "doc03", "start": 1420, "end": 1655}]}
```

これをやらないと、チャンクサイズを変えた瞬間に評価セットが使えなくなる。**この設計がないと、そもそもチャンクサイズの比較実験が成立しない。**

## 5. コーパス

評価に使う文書は、再配布可能なライセンスの公開文書のみを使う。

| 出典 | ライセンス | 用途 |
|---|---|---|
| ウィキペディア日本語版の記事 12 件 | CC BY-SA 4.0 | 検索・生成の評価対象 |

選定の条件は以下。

- 再配布が明示的に許諾されていること（出典・版・ライセンスを `datasets/corpus/LICENSE-NOTICE.md` に記載する）
- 日本語であること（実務で扱う対象に合わせる）
- 1文書あたり数千字程度で、チャンク分割の挙動が観察できる長さがあること
- 個人情報・機微情報を含まないこと

### 選定の結果

分野が偏ると検索の実力が測れないため、内容の重ならない12件を選んだ。

| doc_id | 記事 | 分野 |
|---|---|---|
| `doc01_fujisan` | 富士山 | 地理・自然 |
| `doc02_photosynthesis` | 光合成 | 生物・化学 |
| `doc03_hummingbird` | ハチドリ | 生物 |
| `doc04_iss` | 国際宇宙ステーション | 宇宙開発 |
| `doc05_tcp` | Transmission Control Protocol | 情報技術 |
| `doc06_solar_power` | 太陽光発電 | エネルギー |
| `doc07_constitution` | 日本国憲法 | 法 |
| `doc08_world_heritage` | 世界遺産 | 国際制度 |
| `doc09_edo_period` | 江戸時代 | 歴史 |
| `doc10_tokaido_shinkansen` | 東海道新幹線 | 交通 |
| `doc11_earthquake` | 地震 | 自然科学 |
| `doc12_washi` | 和紙 | 文化・工芸 |

合計 66,496 字。取得と加工は `datasets/fetch_corpus.py` が行い、版ID（oldid）と加工内容は
`datasets/corpus/LICENSE-NOTICE.md` と `datasets/corpus/MANIFEST.json` に残している。
1文書あたり 6,000 字を上限に、段落境界で切り出している。

**加工したテキストがオフセットの基準になる。** 取得条件を変えると評価セットのオフセットが
すべてずれるため、コーパスは取得結果をコミットして固定し、通常は再取得しない。

### この選定の限界

ウィキペディアの記事は生成モデルの学習データに含まれている可能性が高い。
検索側の指標（Recall@k、MRR）は埋め込みの類似度で決まるためこの影響を受けないが、
生成側は、文脈を読まずに記憶から答えても正解に見える余地がある。
ただし本リポジトリの根拠一致率は「回答が合っているか」ではなく
「引用したチャンクが正解根拠と一致するか」を見るため、記憶で答えた場合は
引用が外れて不一致になる。それでもなお、モデルが記事を知っていること自体は
交絡要因として残る。この点は結果を読むときの前提として `docs/04_results.md` にも記す。

## 6. 測定時の固定条件

比較を成立させるために、実験中は以下を固定する。

| 項目 | 値 | 理由 |
|---|---|---|
| temperature | 0.0 | 生成のばらつきを抑える |
| seed | 42 | 同上 |
| 評価セット | 実験期間中は変更しない | 途中で変えると過去の結果と比較できなくなる |
| プロンプト | 実験軸にする場合を除き固定 | 暗黙に変わると原因の切り分けができなくなる |

評価セットを更新した場合は、バージョンを上げて過去の結果と混ぜない。

## 7. 結果の読み方

スコア差をどう扱うかを先に決めておく。

- 評価セットが 50 件規模のため、**数ポイントの差は誤差の範囲**として扱う
- 有意差の主張はしない。「傾向としてこう動いた」までに留める
- 差が出た条件については、個別の質問まで降りて何が起きたかを確認し、考察に書く

この制約を先に書いておくのは、後から都合よく解釈しないため。
